# I Will Get It — project guide for Claude

A full commercial-quality PC game (Windows, macOS, Linux) built in **Godot 4.7.1**.
Goal: anyone in the world can pick it up, enjoy it, and have a good time. No slop, no cheap shortcuts.
We work **one step at a time, studio style**: plan → build → playtest → polish → commit.

Repo: https://github.com/Barrsum/I-Will-Get-It (branch `main`)

## The game

**Premise.** A boy (the hero) finally asked out the girl he loves — she said yes. The night before the
date, he and his best friend (the bro) climb a nearby hill to watch a once-in-1000-years magical
shooting-star cluster. The hero won't stop talking about her, making absurd promises:

> "No matter if the earth is on fire, I will spend every last breath of my life only protecting and being there for her."

…"I'll slay the dragon, fight the alien monsters, climb the mountains, run through the forest…"
The comet passes overhead and **grants every boast literally**. Now he must do all of it to make it to the date.

**Structure.**
- Every level = one boast from the opening scene. Each level has its **own mechanics, objective and camera**,
  each inspired by a classic game/genre (Mario-style platformer, Sonic-style speed run, car race,
  Souls-like boss, shooter, stealth, etc.).
- The hero travels **alone**. The **bro stays on the hill**, can magically see him, and helps **by voice only**
  (radio-style guidance, tutorials, jokes, story). He is the game's narrator and emotional glue.
- Ending: the hero reaches the date.
- Names of hero / girl / bro: **TBD**. Final level list: **TBD** (see `docs/` once the design doc exists).

## Core technical direction

- **3D everywhere, camera/movement locked per level.** 2D-style levels (platformer, speed run) use 3D models
  with a side camera and movement constrained to a plane (2.5D). Top-down for racing, free 3D camera for
  Souls-like, etc. One art pipeline (Blender → `.glb`) serves every level.
- Renderer: **Forward+** (desktop). Base resolution 1920×1080, `canvas_items` stretch, `expand` aspect.
- Language: **GDScript** (statically typed — always annotate types and return types).
- Shared systems (build once, reuse in every level): player/character base, bro dialogue/voice system,
  checkpoint + death/retry flow, input mapping (keyboard + gamepad), save system, scene transitions, settings.
- Each level adds its own mechanics on top of the shared systems; levels must not fork the core.
- **Feel target: Fortnite.** Controls, camera and UI mirror Fortnite (over-right-shoulder camera, crosshair
  centre, sprint/crouch/slide/mantle/aim/emote, bold slanted UI with yellow highlight). Match its *feel*, never its assets.

## Core systems (built)

- **Hero** `scenes/characters/hero/` — `Hero` (CharacterBody3D) owns physics helpers + input buffering
  (jump buffer, coyote, crouch press, aim). Movement modes are `HeroState` nodes under `StateMachine`:
  `Ground`, `Air`, `Crouch`, `Slide`, `Mantle`, `Emote` (names are `Hero.STATE_*` constants). Add a new move =
  add a state node + script; don't grow `hero.gd` with mode-specific logic.
  The body never rotates: facing lives on `VisualRoot`, look direction on `HeroCamera.yaw`.
- **HeroCamera** — top_level rig following the *interpolated* hero transform (physics interpolation is on).
  Framings: normal / aim / sprint FOV / emote (swings to face hero). Crouch lowers the pivot.
- **Hero level rules** — exports `side_scroll` (2.5D: XY-plane lock + side camera; W/S = jump/crouch via the
  `side_jump`/`side_crouch` actions), `can_mantle`, `can_aim`, `force_aim` (rail shooter);
  `set_size_scale()` (power-ups), `set_frozen()` (death/cutscene), `set_spawn()` (checkpoints),
  `controls_enabled`. States must call `hero.move()` (not `move_and_slide()`): it reports contacts to any
  collider with `on_hero_contact(hero, normal, impact_velocity)` (e.g. blocks hit from below).
- **HeroSkin** — the only thing that knows animation names. Placeholder = Quaternius mannequin (UAL1) plus
  the UAL2 clip library (`ual2/…`: Slide_Start/Slide, ClimbUp_1m, Hit_Knockback). Both GLBs are **retargeted
  at import** to Godot's `SkeletonProfileHumanoid` via BoneMaps (`*_bone_map.tres`, generated by
  `tools/make_bone_maps.gd`), so tracks are `%GeneralSkeleton:<HumanoidBone>` and any humanoid clip plays on
  any humanoid model. Our future Blender hero must get a BoneMap too. Godot strips `_Loop` from clip names.
- **Settings** autoload — prefs in `user://settings.cfg`; write via `Settings.set_value()`.
- **Game** autoload — level registry (`Game.LEVELS`, drives the level-select cards), fade scene changes
  (`start_level`, `reload_level`, `restart_level`, `goto_main_menu`, `open_gym`), and per-run state that
  survives a death reload (`checkpoint_index`, `deaths`, `elapsed`). Main scene = `scenes/ui/main_menu.tscn`.
- **Physics layers** — 1 world, 2 hero, 3 enemy, 4 pickup (`Hero.LAYER_*` bit constants).
- **UI** — `UIStyle` (theme + `label()`, `menu_button()`, `add_left_wash()` helpers), `SettingsPanel`
  (shared by main + pause menu), `PauseMenu` (add as a child of any playable level), `HUD` (3D levels).
- **Platformer kit** `scenes/levels/shared/platformer/` — `PlatformerLevel` builds a 2.5D level from an ASCII
  map (legend in its header; 1 cell = `PlatformerArt.CELL` = 1.5 m) and runs the rules: `BumpBlock`, `Coin`,
  `Grumble` (our stompable walker — never call it a Goomba), `PowerMushroom` (super size), `Checkpoint`,
  `Flagpole`, `PlatformerHUD`. `PlatformerArt` owns all placeholder visuals (swap for Blender assets there).
- **Grumble AI** — turns at walls *and* ledges (ground ray ahead), collides with other Grumbles (enemy layer
  in its mask) and both bounce apart.
- **Rail shooter kit** `scenes/levels/shared/rail_shooter/` — `RailShooterLevel` walks the hero down -Z on
  rails (state machine disabled, level drives `hero.move()`), aim is free within `camera.yaw_limit`; `Railgun`
  (hand-mounted, beam FX), `TargetPlate` (NORMAL / BONUS sway / FRIENDLY heart), combo multiplier (+1 per hit,
  max x10; reset on stray shot, escaped target or heart), rank S–C, `ShooterHUD`. Hero skin `set_gun_mode()`
  = AnimationTree blending pistol-aim upper body over walking legs + shoot one-shot.
- **Level 2 "Railgun Alley"** `scenes/levels/level_02/` — sunset street, buildings use `building_facade.gdshader`;
  target waves generated (seeded) in `build_targets()`.
- **LevelHUD** `scripts/ui/level_hud.gd` — shared intro card, toasts, world popups, results card with
  NEXT LEVEL / PLAY AGAIN / MAIN MENU (`Game.next_level()`). Level HUDs extend it.
- **Level 1 "Stomp Road"** `scenes/levels/level_01/` — map in `level_01_map.txt`, generated by
  `tools/level_01_layout.py` (edit the generator, not the txt). The .txt must be included in export filters.
- **Input actions** (project.godot): move_*, look_* (right stick), jump, sprint, crouch, aim, emote, pause, toggle_debug.
- **Test gym** `scenes/levels/test_gym/` — main scene for now; geometry generated by `test_gym_blockout.gd` (@tool).

## Layout

```
assets/      models (.glb), textures, materials, shaders, fonts, audio/{music,sfx,voice}
scenes/      boot/, ui/, characters/, levels/<level_name>/  (scene + its level-specific scripts together)
scripts/     shared code; autoload/ singletons, state_machine/, ui/
addons/      third-party Godot plugins (check license first)
tests/       movement_test (headless regression), screenshot_tour (visual review)
licenses/    full license texts for third-party code that requires it
docs/        design doc, level specs, decisions
```

- Files/folders: `snake_case`. Classes (`class_name`): `PascalCase`. Signals: past tense (`died`, `level_completed`).
- Keep a scene and its script side by side (`player.tscn` + `player.gd`).

## Commands

Godot binaries live in `C:\Godot\` (use the `_console` one from the CLI so output is captured):
`C:\Godot\Godot_v4.7.1-stable_win64_console.exe` — editor GUI: `C:\Godot\Godot_v4.7.1-stable_win64.exe`

- Import / validate project: `<godot> --headless --import` (run from repo root)
- Smoke-run main scene: `<godot> --headless --quit-after 3`
- Run a specific scene: `<godot> --headless --quit-after 60 res://scenes/levels/<x>/<x>.tscn`
- Open editor: `<godot> -e` (or double-click `open_project.bat`); play the game: `play_game.bat`

- **Movement regression test:** `<godot> --headless res://tests/movement_test.tscn` — prints PASS/FAIL per check,
  exit code = failures. Run after any change to hero movement, physics settings or the test gym.
- **Platformer test:** `<godot> --headless res://tests/platformer_test.tscn` — Level 1 rules (15 checks).
- **Shooter test:** `<godot> --headless res://tests/shooter_test.tscn` — Level 2 rules (8 checks).
  A hero death reloads the *current scene* — in a test that restarts the test, so tests must never let the
  hero die except in a final check (and poll for it). Always run with `timeout` in case of a loop.
  (Tests are scenes, not `-s` scripts: `-s` scripts compile before autoloads like `Settings` exist.)
- **Visual review:** `<godot> --resolution 1600x900 res://tests/screenshot_tour.tscn -- <out_dir>` (gym) and
  `res://tests/screenshot_level.tscn` (menus + Level 1 + anim poses) and `res://tests/screenshot_shooter.tscn`
  (Level 2). Needs GPU, no `--headless`. Look at the
  PNGs before calling visual work done.

After changing scenes/scripts, run the import + smoke-run to catch parse/load errors before reporting done.

## Rules

- **Licensing:** we may borrow/learn from open-source projects (movement, cameras, etc.). Only copy code/assets
  under **MIT, BSD, Zlib, Apache-2.0, CC0, CC-BY, OFL (fonts)** (record CC-BY attribution; keep MIT/BSD
  license texts in `licenses/`). **Never GPL/LGPL/CC-NC/CC-ND.**
  Log every third-party item in `CREDITS.md` with source URL + license.
- **No IP copying:** levels are *inspired by* genres/feel. No Nintendo/Sega/etc. characters, names, art, music or sounds.
- **3D assets:** made with the user via Blender MCP, exported as `.glb` into `assets/models/`. Don't commit `.blend1` backups.
- **Git:** small, focused commits with clear messages; push to `origin main` when a step is finished.
  Large binaries (big audio/video/.blend) may need Git LFS later — raise it before adding them.
- The user drives direction; propose, explain trade-offs, then build. Keep the user in the loop each step.
